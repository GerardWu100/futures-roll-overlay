futures-roll-overlay · code walkthrough

Forecasting forward realized variance from futures term structure

What this repository does, how the modules fit together, what each configuration setting changes, and where the code is still weak. Every number on this page came from running the code on the Parquet files in data/raw.

How to use this

Sections follow the order the pipeline runs in. Code blocks are copied from the files under src/futures_roll_overlay/. Coloured boxes carry the plain-English summary, the maths, real sample data, and the traps. This page explains structure and behaviour, not every line.

The process in plain English

A futures contract expires, so a single contract cannot give you a long price history. The code stitches a chain of expiring contracts into one continuous price series per asset, turns that into daily returns, and then asks a forecasting question: given what the futures curve looks like today and how much the market has been moving lately, how much will the market move over the next couple of days? It answers with two models — a simple "tomorrow looks like today" benchmark and a ridge regression — and scores both out of sample. Everything runs offline from local files, with one command.

01What the project is for, and how it is laid out

The research question, taken from README.md: can futures term-structure and lagged volatility features help forecast forward realized variance for a small cross-asset futures set? Three assets are in scope — ES (E-mini S&P 500 equity index futures), CL (WTI crude oil futures) and GC (gold futures) — over calendar year 2024.

Terms used on this page

Futures contract: an agreement to buy or sell something at a fixed price on a fixed future date. Each one expires, so a market like crude oil trades many contracts at once, each for a different delivery month.
Front contract: the nearest one to expiry, normally the most heavily traded.
Roll: switching your position from the expiring contract to the next one.
Term structure: the set of prices for the same asset across delivery months. Its shape is the signal this project uses.
Contango: later delivery months cost more than nearer ones. Backwardation: the opposite.
Realized variance: how much the price actually moved, measured as the sum of squared daily returns. It is the thing being forecast.

FolderWhat lives there
data/raw/futures/One Parquet file per asset, holding daily bars for every contract of that asset. ES has 1042 rows across 8 contracts; CL has 4559 across 24.
data/raw/roll_calendars/Two files per asset. _sample covers 2024 only (313 rows). _full covers 2010-2024 (4694 rows). Each row says which contract was the front contract on that date.
data/raw/manifest/One JSON file describing all of the above: row counts, date ranges, column names, file sizes.
src/futures_roll_overlay/The importable package, split into six stages: data_access, continuous_futures, features, models, evaluation, pipeline.
tests/Eight unit test files plus one integration test that runs the whole pipeline into a temporary folder. 16 tests, all passing.
outputs/runs/One folder per run, named YYYY-MM-DD_NNN. Git-ignored.
blog/, notebooks/, docs/A published write-up, a teaching notebook, and reference notes on the raw-data contract, the target definition, and the evaluation protocol.

Entry points

uv run futures-roll-research                       # the offline pipeline; the normal way in
uv run futures-roll-research --config PATH         # point at a different config.toml
uv run futures-roll-research --output-root PATH    # write artifacts somewhere else
uv run futures-roll-refresh-raw                    # optional: rebuild data/raw from ClickHouse
./scripts/run_research_pipeline.sh                 # three-line wrapper: cd to repo root, then the above
Why the database path is separate

The default run touches no network and no credentials. refresh_clickhouse_raw.py is the only module that imports clickhouse_connect and reads .env, and nothing in the research path imports it. That means the repository can be cloned and run by anyone, and the tests never need a database.

Three public loaders and a settings resolver. Nothing clever happens here, which is the point: this module is the only place that knows where files live.

Why paths climb four parents

The file sits at src/futures_roll_overlay/data_access/raw_cache.py. Four .parent steps from the file itself land on the repository root, so config.toml and data/raw resolve the same way whether you run the pipeline from the repository root, from a notebook, or from a temporary folder in a test. run_research_pipeline.py sits one level deeper in the package but also needs four steps, because it is one folder further along the same depth.

Trap

_read_parquet_with_columns raises rather than repairing. A missing file raises FileNotFoundError with the table name; a missing column raises ValueError listing exactly which columns are absent. There is no silent fallback to an empty frame, so a broken data drop fails at the first read rather than producing a model fitted on nothing.

04Stitching contracts together — build.py

This is the module where quantitative futures work actually happens, and it is where the most serious defect in the repository was found. Two decisions are made here: which contract is the front contract on each day, and how to remove the price jump that appears when the front contract changes.

Choosing the front contract

def _calendar_roll(daily_data, roll_calendar):
    """Select front contract from explicit roll calendar mapping."""
    merged = roll_calendar.merge(
        daily_data, how="left",
        left_on=["date", "contract"], right_on=["date", "symbol"],
    )
    merged = merged.dropna(subset=["close"]).reset_index(drop=True)
    active_contracts = merged.set_index("date")["contract"]
    roll_dates = _extract_roll_dates(active_contracts=active_contracts)
    front_prices = merged.loc[:, OUTPUT_COLUMNS].copy()
    return front_prices, roll_dates, active_contracts
In plain words

The calendar says "on this date, the front contract is this one". Join that to the price table and you have one price series. A roll date is any day where the named contract differs from the day before.

What it does

Input: the full contract-level price panel and a date, contract calendar. Output: a single-row-per-date price frame, the list of roll dates, and a date-indexed series of active contract names. Role: reduces many contracts to one series. The alternative, _volume_roll, answers the same question by picking the highest-volume contract each day, with the symbol name as a deterministic tie-break.

Removing the roll jump

On 13 March 2024 the ES front contract was ES_H24 at 5173.25. On 14 March it was ES_M24 at 5217.00. Nothing happened in the equity market to justify a 0.85% gap; the two numbers are simply prices of two different contracts. A back-adjustment removes that gap so the stitched series behaves like a single tradable instrument.

def _roll_boundary_closes(adjusted, current_index, roll_timestamp,
                          active_contracts, contract_closes):
    """Return (outgoing_close, incoming_close) for one roll boundary.

    Both legs are read from the last session before the roll, where the
    outgoing and the incoming contract normally both trade. Measuring them on
    the same session isolates the price difference between the two contracts,
    which is the only part a back-adjustment should remove.
    """
The formula

Let $p$ be the last session before a roll, $O$ the outgoing contract and $N$ the incoming one. The ratio adjustment scales every price on or before $p$ by

$$f=\frac{C_{N,p}}{C_{O,p}}$$

and the Panama adjustment adds

$$g=C_{N,p}-C_{O,p}$$

$C_{N,p}$ is the close of the incoming contract on session $p$, and $C_{O,p}$ the close of the outgoing contract on the same session $p$. Both legs share the session, so $f$ and $g$ contain only the difference between the two contracts. Roll dates are walked newest to oldest, so each earlier segment picks up the product of every later factor.

The adjusted level on 12 and 13 March is far above the raw level because those two days also carry the factors from the June, September and December rolls, applied later in the loop.

Trap: this is the bug that was fixed

The original code took the outgoing close from session $p$ and the incoming close from the roll session itself, one day later. That factor contains the roll gap plus one day of genuine market movement, so after adjustment the roll-day return of the stitched series was exactly zero, every time. For crude oil that meant 12 forced zeros out of 308 observations. On 14 October 2024 the same-day contract ratio was 0.9909, but the cross-session ratio was 0.9525 — a real 3.9% one-day move in crude oil was misclassified as a roll gap and erased. Since the entire project forecasts realized variance, deleting the largest daily moves of the year is not a rounding error.

Why ratio rather than Panama by default

Panama adds a constant to every earlier price. That preserves absolute price differences but distorts percentage returns, and it can drive very old prices negative over long histories. Ratio adjustment preserves percentage returns exactly within each segment, which is what a study of squared returns needs. Both are implemented; the config picks one.

05Curve shape features — term_structure.py

Three numbers and one label per day, describing the shape of the futures curve.

MONTH_CODE_TO_MONTH = {"F":1,"G":2,"H":3,"J":4,"K":5,"M":6,
                       "N":7,"Q":8,"U":9,"V":10,"X":11,"Z":12}

def _parse_contract_expiry(contract_symbol: str) -> pd.Timestamp:
    """Parse a contract code such as ``ES_H24`` into an expiry proxy date."""
    _root, expiry_code = contract_symbol.split("_", maxsplit=1)
    month_code = expiry_code[0]
    year_suffix = expiry_code[1:]
    month_number = MONTH_CODE_TO_MONTH[month_code]
    year_number = 2000 + int(year_suffix)
    return pd.Timestamp(year=year_number, month=month_number, day=1)
Syntax: the exchange month code

Futures symbols encode the delivery month as a single letter. ES_H24 is the March 2024 E-mini S&P contract; H is March, M June, U September, Z December. Crude oil uses all twelve letters because it has a monthly cycle. The parsed date is the first of the delivery month, which is only a proxy — real expiry is later in the month — but it is exact enough to sort maturities into order.

The formula

Let $F_1$ be the close of the nearest contract on a given day and $F_2$ the close of the next one. The three features are

$$\text{spread}=F_2-F_1$$

$$\text{roll yield}=\frac{F_1-F_2}{F_2}\cdot\frac{365}{d}$$

$$\text{slope}=\text{the ordinary least squares slope of }\left(\frac{F_k}{F_1}\right)\text{ against }k=0,1,\ldots,K-1$$

$d$ is the number of calendar days between the two contracts' end dates, floored at 1. The factor $365/d$ turns a gap-period return into an annual rate, using calendar days because $d$ is a calendar-day count. $K$ is num_contracts, here 3, so $k$ runs 0, 1, 2. Dividing by $F_1$ makes the slope comparable across assets priced at very different levels. Note the sign: roll yield is positive when the near contract is dearer, that is in backwardation.

The slope shortcut holds because with three equally spaced ranks the least-squares slope is just half the rise from the first point to the last. Across the whole pooled dataset of 924 rows the regime labels split 579 contango, 325 backwardation, 20 flat — ES is in contango on all 308 of its days, CL in backwardation on 291 of its 308.

Why regime labelling has a persistence rule

_apply_regime_persistence refuses to switch label until a challenger has appeared for regime_persistence_days consecutive observations. Without it, a roll yield sitting close to the flat threshold would flip the label back and forth daily and the one-hot columns would become noise. At the shipped value of 1 the rule is off, so this is a lever waiting to be used rather than one currently doing work.

Trap: two different sources of time

The denominator $d$ can come from two places: the roll calendar, which dates the session a contract stopped being the front contract, or the month-code proxy, which dates the first of the delivery month. They are on different scales. Reading one leg from each was producing a gap of 18 days between ES_Z24 and ES_H25, contracts a full quarter apart, which inflated the annualized roll yield roughly fivefold. _maturity_gap_days now insists both legs come from the same source. See Fixes applied.

06The forecasting target — realized_variance.py

One function, and it is the most timing-sensitive code in the repository. Getting the target off by one day would make every result meaningless.

squared_returns = log_returns.pow(2)
# Build the target from explicit leads. A shifted rolling window still
# looks backward and would attach r_t^2 + ... + r_{t+H-1}^2 to date t.
future_squared_returns = [
    squared_returns.shift(-lead) for lead in range(1, horizon_days + 1)
]
forward_sum = pd.concat(future_squared_returns, axis=1).sum(
    axis=1, min_count=horizon_days,
)
trailing_sum = squared_returns.rolling(
    window=horizon_days, min_periods=horizon_days,
).sum()
In plain words

For each day, add up the squared returns of the next $H$ days — that is what we are trying to predict. Separately, add up the squared returns of the last $H$ days including today — that is what we already know, and it becomes the benchmark forecast.

The formula

With $r_t$ the daily log return, the daily realized variance is

$$rv_t=r_t^2$$

the forward target over $H$ days is

$$RV_{t,t+H}=\sum_{i=1}^{H}r_{t+i}^2 \qquad RV^{ann}_{t,t+H}=\frac{A}{H}\,RV_{t,t+H}$$

and the benchmark, using only information available after the close on day $t$, is

$$K_t=\frac{A}{H}\sum_{i=0}^{H-1}r_{t-i}^2$$

$H$ is target_horizon_days, here 2. $A$ is annualization_factor, here 252 trading days per year. The sum for the target starts at $i=1$, so day $t$'s own return is excluded; the sum for the benchmark starts at $i=0$, so day $t$'s own return is included. That one index is the whole difference between a forecast and a peek at the answer.

The first row has no benchmark and the last two rows have no target, both by construction. Those rows are dropped later, which is why 311 return observations become 308 modelling rows.

Why explicit leads instead of a shifted rolling window

A rolling sum in pandas always looks backwards. Writing rolling(H).sum().shift(-H) is tempting but attaches $r_t^2+\ldots+r_{t+H-1}^2$ to date $t$ — it includes day $t$'s own return, which is already known when the forecast is made. That single contamination would inflate the apparent skill of any model. Building the sum from shift(-1) through shift(-H) makes the intent impossible to misread. The min_count=horizon_days argument matters too: without it pandas would treat a partly-missing sum as valid and produce a short target at the end of the sample.

Why one-hot columns instead of a text label

pd.get_dummies turns the regime label into three 0/1 columns because a linear model cannot consume the string "contango". Because each asset only sees the regimes it actually visits, ES ends up with one dummy column and CL with three. The pipeline's _align_asset_datasets fixes that by taking the union of columns across assets and filling the absent ones with 0, so every asset ends up with the same design matrix.

08The two models — baselines.py, train.py

The benchmark

def trailing_variance_persistence(trailing_variance: pd.Series) -> pd.Series:
    """Use the latest observable trailing variance as the forward forecast."""
    prediction = trailing_variance.copy()
    prediction.name = "prediction"
    return prediction
In plain words

Forecast that the next two days will be as volatile as the last two days were. That is the whole model. Any real model has to beat it.

Why a two-line function earns its own module

Because the honest version of it is easy to get wrong. The tempting shortcut is to shift the target series back and call it persistence, but that answer is not available at forecast time. This version takes $K_t$, which sums returns up to and including day $t$ and nothing beyond, so a trader could genuinely have produced it.

Ridge regression

def _ridge_closed_form(design_matrix, target_vector, alpha):
    """Solve ridge coefficients with closed-form normal equations."""
    feature_count = design_matrix.shape[1]
    identity = np.eye(feature_count)
    # Do not penalize the intercept column in the ridge penalty matrix.
    identity[0, 0] = 0.0
    left_hand_side = design_matrix.T @ design_matrix + alpha * identity
    right_hand_side = design_matrix.T @ target_vector
    return np.linalg.solve(left_hand_side, right_hand_side)
The formula

Ordinary least squares minimises the sum of squared errors. Ridge adds a penalty on the size of the coefficients:

$$\hat\beta=\arg\min_{\beta}\;\lVert y-X\beta\rVert^2+\alpha\lVert\beta_{1:}\rVert^2$$

Setting the derivative with respect to $\beta$ to zero gives the closed form the code solves:

$$\left(X^{\top}X+\alpha I_0\right)\hat\beta=X^{\top}y$$

$y$ is the target vector, one entry per training row. $X$ is the design matrix: a column of ones followed by the standardized features. $\alpha$ is ridge_alpha, here 1.0. $I_0$ is the identity matrix with its top-left entry set to zero, so the intercept escapes the penalty. $\beta_{1:}$ means all coefficients except the intercept. Features are standardized first, using

$$z_j=\frac{x_j-\mu_j}{\sigma_j}$$

where $\mu_j$ and $\sigma_j$ are the mean and population standard deviation of feature $j$ in the training rows only. A feature with zero spread has its $\sigma_j$ replaced by 1 so the division stays finite.

Why standardize before penalizing

The penalty $\alpha\lVert\beta\rVert^2$ treats every coefficient the same. Without standardization that is arbitrary: spread is measured in index points around 59, while lag_rv_1 is around $5\times10^{-5}$. The raw coefficient on lag_rv_1 would have to be enormous to matter, and the penalty would crush it purely because of the unit it is measured in. Standardizing puts all features on the same scale so the penalty is a statement about importance rather than about units.

Why the intercept is not penalized

Shrinking the intercept toward zero would pull predictions toward zero variance, which is not a neutral prior — variance is strictly positive and typically around 0.02 annualized here. Leaving the intercept free lets it absorb the average level of the target so the penalty only shrinks the part of the model that responds to features.

09Scoring out of sample — walk_forward.py, metrics.py

while True:
    train_end = test_start - label_horizon_days
    test_end = test_start + test_size - 1
    if test_end >= row_count:
        break
    splits.append(WalkForwardSplit(train_start=train_start, train_end=train_end,
                                   test_start=test_start, test_end=test_end))
    test_start = test_start + step_size
In plain words

Train on the early rows, predict the next twenty, slide forward twenty rows, repeat. Crucially, throw away the last few training rows, because their answers had not happened yet at the moment the forecast is made.

The formula

A training label dated $s$ is the sum of squared returns on days $s+1$ through $s+H$, so it is only known once day $s+H$ has closed. If the first test row is at position $T$, a training label is usable only when

$$s+H\le T \quad\Longrightarrow\quad s\le T-H$$

so the last usable training row is $T-H$, and

$$\text{purged rows}=(T-1)-(T-H)=H-1$$

$s$ is the row position of a training observation, $T$ the row position of the first test observation, $H$ the forecast horizon in rows. With $H=2$ exactly one row is discarded per fold. If $H$ were 21 for a monthly horizon, 20 rows would go, and the protection would matter a great deal more.

Training always starts at row 0, so the window expands rather than sliding. Eleven folds times twenty test rows gives 220 predictions per model per asset, and 220 x 3 assets x 2 models = 1320 rows in predictions.parquet.

Why standardization is recomputed on each fold's training rows

_ridge_test_predictions fits the mean and standard deviation on the training slice alone, then applies those same numbers to the test slice. If it had standardized the full dataset once up front, the training rows would carry information about the mean and spread of future data, and the out-of-sample score would be optimistic. The cost is that the same standardizer is computed twice, once inside fit_ridge_regression and once outside it, which is wasteful but not wrong.

The four metrics

With $y_i$ the observed forward variance and $\hat y_i$ the prediction over $n$ test rows:

$$\text{MSE}=\frac{1}{n}\sum_i(y_i-\hat y_i)^2 \qquad \text{RMSE}=\sqrt{\text{MSE}} \qquad \text{MAE}=\frac{1}{n}\sum_i\lvert y_i-\hat y_i\rvert$$

$$R^2=1-\frac{\sum_i(y_i-\hat y_i)^2}{\sum_i(y_i-\bar y)^2}$$

$\bar y$ is the mean of the observed values within that test window. $R^2$ is negative whenever the model does worse than simply predicting that window's own average — and because that average is not knowable in advance, a negative $R^2$ here is a weaker indictment than it looks. It is still a fair comparison between the two models, since both are scored the same way.

Why evaluation is per asset rather than pooled

The pooled table has three rows per date, one per asset. Walk-forward splitting works on row positions, so a pooled split would cut through the middle of a date and mix assets across the train and test boundary. Running each asset separately keeps row position and calendar date in one-to-one correspondence. The pooled numbers in metrics.csv are then simply averages of per-asset fold metrics, not a separate pooled fit.

Trap: the coefficient file is in-sample

feature_importance.csv comes from full_fit, a single ridge fit on all rows of all assets with no holdout. It is a description of which features the model leans on, not evidence that they work. The out-of-sample evidence is in metrics.csv, and it is not flattering.

12Fixes applied

Four defects were found while reading the code and were fixed. All 16 tests still pass and ruff check src tests is clean.

WhereWhat was wrongEvidenceThe fix
quant
continuous_futures/build.py		 The roll adjustment factor was built from the outgoing contract's close on one session and the incoming contract's close on the next session. That factor contains one day of genuine market movement as well as the contract gap, so after adjustment every roll-day return was exactly zero. All 21 roll days across ES, CL and GC had a log return of exactly 0. On 14 October 2024 the true CL contract ratio was 0.9909 while the cross-session ratio was 0.9525; a 3.9% oil move was deleted. New _roll_boundary_closes reads both closes from the last session before the roll, using a wide close panel built by _contract_close_panel. Cross-session values remain only as a fallback when the incoming contract has no bar that day, which never happens in the shipped data.
quant
features/term_structure.py and pipeline/run_research_pipeline.py		 The maturity gap in the roll-yield denominator could take one end date from the roll calendar and the other from the month-code proxy. The two are on different scales. Worse, the newest contract's calendar end date is where the file stops, not where the contract rolled out. For ES the gap between ES_Z24 and ES_H25 came out as 18 days instead of about 90, inflating the annualized roll yield roughly fivefold: roll_yield jumped from $-0.0388$ to $-0.1765$ overnight on 22 September 2024. That single feature jump drove one walk-forward fold to $R^2=-1828$. _maturity_gap_days now takes both end dates from the same source. The pipeline drops any contract whose calendar end date equals the calendar's last date, since that date is a censoring artifact. Post-fix the same day reads $-0.0353$, and the worst fold improved from $R^2=-1828$ to $-32$; pooled ridge $R^2$ went from $-56.0$ to $-1.39$.
data
pipeline/run_research_pipeline.py		 close_series.pct_change().fillna(0.0) invented a return of exactly zero for the first session of the sample, which then flowed into the realized-variance series as a day on which the market did not move. ES showed 2024-01-02 log_return 0.000000, daily_realized_variance 0.0. Changed to .dropna(). The first session simply has no return. ES goes from 312 to 311 return observations and from 309 to 308 modelling rows.
reporting
evaluation/metrics.py and pipeline/run_research_pipeline.py		 With no overlapping observations, compute_regression_metrics returned mse=0.0, rmse=0.0, mae=0.0, r2=0.0, and _mean_fold_metrics did the same for an empty fold list. Zero error reads as a perfect model. Latent rather than active: the shipped configuration always produces non-empty folds. It would fire if train_size were set past the end of an asset's history. Both now return NaN, which propagates to metrics.csv as an empty cell instead of an impressive zero.
What this means for the existing artifacts

Everything under outputs/runs/ and the numbers in blog/ were produced before these fixes and are now stale. They were left untouched, because regenerating them is a separate decision. Re-running uv run futures-roll-research produces the corrected figures shown in section 11.

Considered and deliberately not changed

Several things look odd but are defensible design choices rather than defects, so they were left alone: evaluating each asset separately instead of pooling; excluding known_trailing_rv_annualized from the ridge feature set; returning $R^2=0$ when the observed values in a test window are all identical; the expanding rather than rolling training window; and the hard-coded 365 in the roll-yield annualization, which is correct because the gap is measured in calendar days.

16Limitations, stated honestly

Both models lose to the test window's own average

Every $R^2$ in metrics.csv is negative. Ridge does beat persistence on squared error, which is the comparison the project set out to make, but neither model is useful in an absolute sense on this sample.

The sample is one calendar year and three assets

308 rows per asset, 11 folds, 220 out-of-sample predictions per model per asset. Any metric computed on that is dominated by a handful of volatile days. A two-day horizon on one year of data cannot separate a real effect from luck.

Term-structure features jump at every contract roll

spread is a raw price difference between two specific contracts. When the front pair changes, its level shifts. The ridge model standardizes on pre-roll training rows and then extrapolates through that shift. That is why one ES fold still scores $R^2=-32$ even after the timing fix. A more careful version would either roll-adjust the term-structure features too, or express the spread as a percentage of the front price.

The slope feature is built on nearly untraded prices

On 2 January 2024 the third ES contract traded 3 lots against the front contract's 1.5 million. Its close is a stale quote, so the third point of the curve carries little information and a lot of noise. num_contracts = 3 was chosen to make the slope estimable, not because the third point is reliable.

The stitched series and the term-structure features can disagree about the front contract

The roll calendar switched ES to M24 on 14 March, but the contract-level panel still had H24 bars until 15 March, so the term-structure code kept treating H24 as the front contract for two more days. It is a one- or two-day mismatch, but it means the price series and the curve features are not always describing the same contract.

The environment in the repository is broken

.venv cannot import NumPy: it fails with "Something is wrong with the numpy installation", and uv sync reports nothing to do. Every number on this page was produced by running the package with PYTHONPATH=src in a clean throwaway environment on Python 3.13 with NumPy, pandas, PyArrow and Matplotlib. Deleting .venv and re-running uv sync --all-groups should rebuild it.
